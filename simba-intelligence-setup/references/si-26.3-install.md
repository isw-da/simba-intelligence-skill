# Simba Intelligence 26.3: install through the Logi Composer chart

Written 2 October 2026 from public sources only. Every claim below names the URL or
command it came from, so a reader can re-check it before relying on it.

## What changed at 26.3

From 26.3, Simba Intelligence (SI) installs as a sub-component of the Logi Composer
Helm chart. The public docs call the Composer product Self-Service Analytics. You turn
SI on with `simbaIntelligence.enabled: true` in the Composer chart's values.

The standalone `simba-intelligence-chart` has no 26.3 release on Docker Hub. Its tags
at the time of writing are `26.2.1` (the newest GA) and `26.3.0-SNAPSHOT`, and a
snapshot is not a release. Check this yourself:

```bash
curl -s "https://hub.docker.com/v2/repositories/insightsoftware/simba-intelligence-chart/tags?page_size=20&ordering=last_updated" \
  | python3 -c "import json,sys; [print(t['name']) for t in json.load(sys.stdin)['results']]"
```

The SI application image did move to 26.3: `insightsoftware/simba-intelligence:26.3`
(25 September 2026) and `insightsoftware/zoomdata:26.3.0` (29 September 2026) are both
on Docker Hub, with new `26.3.0-k3s` tags beside them.

So there are two paths:

- **Existing 26.2.x installs** made from `simba-intelligence-chart` keep using the
  existing guides (`deployment-local.md`, `deployment-cloud.md` and the rest). This repo
  does not yet document a move from a standalone 26.2 install to the Composer chart.
- **New 26.3 installs** use the Composer chart, as below.

The public install page says: "Kubernetes is supported for new installations only for
version 26.3 and later." Source:
https://insightsoftware.mintlify.app/simba-embedded-analytics/docs/self-service-analytics/26.3/administer/install/kubernetes-ov.md

## Step 1: add the Composer Helm repository

```bash
helm repo add composer https://composer-repo.logianalytics.com/helm-charts/stable
helm repo update composer
helm search repo composer/composer --versions | head -5
```

`helm repo add` registers the public chart repository under the local name `composer`.
`helm search repo ... --versions` lists every chart version with the application
version it ships. Chart versions and application versions are numbered separately:

| Chart version | Application version | Published |
|---|---|---|
| 1.22.0 | 26.3 | 2026-09-29 |
| 1.21.0 | 26.2 | 2026-06-29 |
| 1.20.0 | 26.1 | 2026-03-16 |

Source: `helm search repo composer/composer --versions` against the repository above (the
publish dates are in each version's description).

## Step 2: read the chart's own values before writing yours

```bash
helm pull composer/composer --version 1.22.0 --untar
less composer/values.yaml        # search for "simbaIntelligence:"
```

`helm pull --untar` downloads the chart and unpacks it into `./composer`, so you can
read `values.yaml` and the templates offline. Every key in this guide comes from that
file. If a later chart version disagrees with this guide, the chart wins.

What chart 1.22.0 says about SI:

- `simbaIntelligence.enabled` is `false` by default. When it is false, the chart renders
  none of the SI resources.
- With it on, the chart adds the SI database (`simbaintelligence`) and its Alembic
  migration Job (`simbaIntelligence.dbMigrate`), the REST API (`simbaIntelligence.website`,
  service port 5050), a Celery worker and beat (`simbaIntelligence.celery.worker`,
  `simbaIntelligence.celery.beat`) and Redis (`simbaIntelligence.redis`).
- The MCP server (`simbaIntelligence.mcp`, service port 8001) is a second opt-in:
  `simbaIntelligence.mcp.enabled` is `false` even when SI is on.
- `simbaIntelligence.composerPublicUrl` is the browser-reachable Composer URL, and SI
  needs it. Left empty, the chart derives an `https://` URL from the first ingress or
  Gateway API hostname plus `zoomdataWeb.contextPath`. With no hostname and no
  override, the install still succeeds: the chart's `NOTES.txt` prints a warning, and
  SI fails later at runtime. Set a hostname or the URL itself.
- SI is served under `<zoomdataWeb.contextPath>/intelligence`. The default
  `zoomdataWeb.contextPath` is `/composer`, so SI sits at `/composer/intelligence`.
- The MCP endpoint is always at the root path `/mcp`, with its OAuth discovery
  metadata at `/.well-known`. Neither sits under the context path.
- `zoomdataWeb.adminPassword`, or `zoomdataWeb.existingSecret` naming a Secret that
  holds it, sets the built-in `admin` user's password at install. With SI enabled this
  is a hard requirement: `templates/simba-intelligence-validation.yaml` fails the
  install when neither is set, because SI calls Composer's API as that user.
- The chart's internal PostgreSQL uses image `postgres:18` and database user
  `zoomdata`, and creates the databases `zoomdata`, `zoomdata-upload`,
  `zoomdata-keyset`, `zoomdata-user-auditing`, `zoomdata-qe`, `zoomdata-config` and
  `simbaintelligence`.

Source for all of the above: `helm pull composer/composer --version 1.22.0 --untar`,
files `composer/values.yaml`, `composer/templates/_helpers.tpl` and
`composer/templates/simba-intelligence-validation.yaml`.

## Step 3: write the values file

A minimal values file for an install behind an ingress with a real hostname and TLS.
Replace the hostname, the Secret name and the password placeholder.

```yaml
# composer-si-values.yaml
zoomdataWeb:
  contextPath: /composer                 # chart default, shown so it is explicit
  adminPassword: "<admin-password>"      # or set zoomdataWeb.existingSecret instead

ingress:
  hosts:
    - composer.example.com
  tls:
    - secretName: composer-tls           # a kubernetes.io/tls Secret that already exists
      hosts:
        - composer.example.com

simbaIntelligence:
  enabled: true
  # Optional when ingress.hosts is set: the chart derives the same value.
  composerPublicUrl: https://composer.example.com/composer
```

Do not commit a real password into a values file. `zoomdataWeb.existingSecret` reads
the admin password (and the other credentials the chart lists beside it in
`values.yaml`) from a Secret you create yourself.

### Optional: the MCP server

Only add this if you want MCP clients to reach SI.

```yaml
simbaIntelligence:
  enabled: true
  mcp:
    enabled: true
    # Origin only: scheme and host, no path. Empty derives https://<first ingress host>.
    baseUrl: https://composer.example.com
```

The chart comments say three things worth knowing before you turn it on. `baseUrl` is
the origin only; a path on it doubles up as `/mcp/mcp` and breaks the OAuth issuer. It
is always `https`, because the MCP server refuses to start with a real hostname over
plain `http`. And making that hostname reachable over TLS is the operator's job.

## Step 4: install

```bash
helm install composer composer/composer \
  --version 1.22.0 \
  -f composer-si-values.yaml \
  --namespace composer \
  --create-namespace
```

`composer` (the first word after `install`) is the release name, and `composer/composer`
is the repository and chart. `--version 1.22.0` pins the chart that ships 26.3. The
release name and namespace here are examples; choose your own.

## Step 5: check the versions you are running

Once the pods are ready, ask each component which version it is. Use your own scheme,
host and context path.

```bash
# SI: base path is <contextPath>/intelligence
curl -s https://composer.example.com/composer/intelligence/api/v1/version

# Composer
curl -s https://composer.example.com/composer/api/version
```

On an install of chart 1.22.0, SI's `/api/v1/version` returned `version` `26.3.0` and
`db_version` `4e6e81bb64b6`, and Composer's version endpoint returned `26.3.0`. That
observation was made at `/discovery/api/version` for Composer; on your install the
path follows your own `zoomdataWeb.contextPath`.
